OVERVIEW

Why ADOMs Exist

Without ADOMs, all devices and their policies live in a single flat management space. Any admin can see and edit any object — and changes ripple silently across every business unit referencing that object. ADOMs solve this by creating isolated containers, each with their own devices, policy packages, and objects.

Core idea: ADOMs are isolation containers. RBAC controls who can access what — ADOMs control what exists in the same space at all. They solve the silent blast radius problem.
ADOM — Administrative Domain
An isolated management container within FortiManager. Each ADOM has its own set of managed devices, policy packages, and objects. Changes inside one ADOM cannot affect another.

The Shared Object Problem

Imagine two business units — BU1 and BU2 — both reference an address object called Corp-Server. An admin for BU1 renames or changes it. BU2's policies now silently reference the wrong object. No warning. No log. Traffic breaks.

!
COMMON MISTAKE
RBAC alone does not prevent this. Even if BU1's admin can't access BU2's policies, they can still modify shared objects in a flat space. ADOMs are the architectural fix — not access controls.
≈
ANALOGY
ADOMs are like separate office floors in a building. RBAC is the keycard system. The keycard stops people walking in — but without separate floors, one person's renovation still affects everyone on the same level.
GLOBAL ADOM · POLICY & OBJECTS

The Global ADOM

The Global ADOM sits above all regular ADOMs. It does not manage devices directly — instead it pushes policy and objects down into regular ADOMs. It is how central security teams enforce organisation-wide rules without touching local admin spaces.

Header and Footer Policies

The Global ADOM uses Global Policy Packages split into two layers:

Policy Layer When It Fires Typical Use
Header Policy Before the local ADOM policy package Enforce blocklists, mandatory deny rules, corporate security baseline
Local Policy Package Middle — normal per-ADOM policy logic Business unit specific allow/deny rules
Footer Policy After the local ADOM policy package Default-deny catch-all, explicit logging, implicit fallback
≈
ANALOGY
Header = bouncer at the door. Footer = net under the trapeze. Everything in between is the local act. The global team controls the venue — local teams run their own show inside it.

Global Objects and the g_ Prefix

When the Global ADOM pushes objects down to local ADOMs, those objects receive a g_ prefix. This marks them as globally managed.

  • Local admins can use g_ objects in policies — they appear as selectable options
  • Local admins cannot edit g_ objects — they are read-only at the local level
  • Changes to global objects must be made in the Global ADOM and pushed down again
★
EXAM NOTE
The g_ prefix is a key signal in exam scenarios. If you see it, the object is globally managed and cannot be modified locally — even by a super-admin of that ADOM.
DEVICE REGISTRATION · AUTHORISATION

Device Registration & Authorisation

When a FortiGate is first configured to be managed by FortiManager, it initiates the connection — not the other way around. FortiManager does not reach out. The device presents itself and waits to be authorised.

FortiGate initiates → Appears in FMG as Unregistered / Pending → Admin reviews → Authorised → Assigned to ADOM

The Two Checks

Before authorisation, FortiManager performs two verification checks on the connecting device:

1
Certificate Check — Confirms this is a legitimate Fortinet FortiGate device. The certificate is signed by Fortinet. This answers: "Can we trust this device?"
2
Serial Number Check — Confirms this is the specific device that should be here. Every FortiGate has a unique serial number. This answers: "Is this the right device?"
!
COMMON MISTAKE
Never enable auto-accept in production. Without manual authorisation, a rogue device with a valid Fortinet certificate could join your management plane undetected. The serial number check is your second line of defence.
→
TIP
Until authorised, the FortiGate appears as unregistered and FortiManager manages nothing on it. Authorisation is the gate — nothing happens before it.
POST-AUTHORISATION · MANAGEMENT FLOW

The FortiManager Management Flow

After a device is authorised, there is a specific sequence of steps before FortiManager can safely manage it. Getting this order wrong in production causes outages.

1
Retrieve Config — Pull the existing live config from the FortiGate up into FortiManager's database. This gives FMG an accurate baseline. Never skip this on a device that has been running in production.
2
Assign Policy Package — Attach a policy package to the device. Policy packages are centrally managed sets of firewall rules that can be shared across multiple devices.
3
Configure Dynamic Interfaces — Map logical interface names in the policy package to the actual physical interfaces on this specific device.
4
Install — Push the policy package and device settings down from FortiManager to the FortiGate. This is a one-way push. FMG becomes the source of truth.
!
COMMON MISTAKE
Pushing before retrieving on a live device will overwrite the running config with whatever FMG currently has — which may be empty or outdated. This is a production outage. Always retrieve first.

Policy Packages & Dynamic Interfaces

A policy package is a reusable set of firewall rules managed in FortiManager. One package can be assigned to many FortiGates — but each device may have different physical interface names.

Concept What It Does Why It Matters
Policy Package Central set of firewall rules in FMG Change once, push everywhere — no per-device duplication
Dynamic Interface Logical interface name in the package Abstracts away physical interface name differences per device
Per-Device Mapping Maps logical → physical per FortiGate Device A maps "WAN" to wan1, Device B maps "WAN" to port3
≈
ANALOGY
The policy package is the blueprint. Per-device mappings are the address labels on each building. The blueprint is identical — but each building has its own front door in a different location.

Source of Truth & Local Changes

Once a device is under FortiManager management, FortiManager is the source of truth. The FortiGate runs whatever was last installed from FortiManager — not whatever currently exists in FortiManager's database.

SCENARIO — EXAM QUESTION STYLE
A junior admin SSHes into a managed FortiGate and adds a local firewall policy. The next day a senior admin installs the policy package from FortiManager. What happens to the local change?
Answer: The local change is overwritten. Install pushes FMG's version of the config DOWN to the FortiGate. The local addition was never in FMG's database, so it does not survive the install. The lesson: never make local changes on a FortiManager-managed device.
≈
ANALOGY
FMG = master script. FortiGate = the actor. You do not let the actor improvise — the next rehearsal will reset them to the script anyway.
EXAM TIPS

What the Exam Focuses On

FortiManager questions typically test your understanding of the management flow sequence, ADOM isolation logic, and the consequences of misconfigured or out-of-order operations. Expect scenario-style questions that describe a symptom and ask for root cause or correct next step.

TRAP 01
Push Before Retrieve
On a live device, pushing before retrieving will overwrite the running config. Always retrieve first.
TRAP 02
Auto-Accept in Production
Never enable auto-accept. Rogue devices with valid certs could join management without review.
TRAP 03
Local Changes on Managed Device
Any local change is overwritten on the next install from FortiManager.
TRAP 04
g_ Objects Are Read-Only
Global objects pushed to ADOMs cannot be edited locally. They must be changed in the Global ADOM and re-pushed.

Key Exam Distinctions

  • Retrieve ≠ Import — The correct FortiManager term is retrieve. Import is not the right word for this operation
  • Install is one direction only — FMG pushes DOWN to the FortiGate. There is no automatic retrieve during an install
  • Out of sync status — FortiManager flags devices as out of sync when changes exist in FMG that haven't been installed yet
  • FortiManager shows what should be — the FortiGate shows what is currently running. Both are telling the truth within their own context
  • Header fires before local, Footer fires after — know the order and know which type of rule goes where
  • Two registration checks — certificate (legitimacy) AND serial number (identity). Both are required
★
EXAM NOTE
If a question describes a FortiGate with missing policies after a FortiManager install — look for a scenario where local changes were made directly on the device before the install. The install is the cause, not a bug.
