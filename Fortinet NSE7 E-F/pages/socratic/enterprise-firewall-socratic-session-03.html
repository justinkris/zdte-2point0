OVERVIEW

Policy Package Model

FortiManager uses a two-layer architecture — a device layer and a policy layer. The policy layer is where policy packages live. A single package can be assigned to many FortiGate devices, making centralised management of large deployments possible.

Core idea: One policy package → many devices. Per-device mapping handles the differences between them.
POLICY PACKAGE
A named collection of firewall policies and objects stored in the FortiManager policy layer. Assigned to one or more FortiGate devices. Changes do not reach FortiGate until explicitly installed.
DEVICE LAYER
Stores device-specific settings — network config, VPN, system, log. Has its own revision history per device. Separate from the policy layer.
POLICY LAYER
Stores policy packages, objects, security profiles, and normalised interfaces. Changes here only apply after an install or reinstall operation.
≈
ANALOGY
Think of the policy package as a master template for a franchise. Every branch runs the same rules — but the LAN subnet, the port names, and the IP pools are swapped out per location. The template is one. The values are local.
TOPIC A · PER-DEVICE MAPPING

Dynamic Objects & Per-Device Mapping

When 50 branches share one policy package but have different LAN subnets, FortiManager uses per-device mapping to resolve the difference. One object name, different values per device.

How It Works

An address object called LAN_subnet exists once in the policy layer. Each device has its own mapped value. At install time, FortiManager substitutes the correct value for each device automatically.

★
EXAM NOTE
Per-device mapping works for simple, swappable values — addresses, VIPs, IP pools. It does NOT work for complex security profiles like Web Filter or Antivirus — those need unique object names per device.

What Supports Per-Device Mapping

Object TypeSupports MappingWhy
Firewall Addresses✅ YesSingle IP/subnet value — easy to swap
Virtual IPs / VIP Groups✅ YesSingle mapped IP — swappable
IP Pools / IPv6 Pools✅ YesSingle value per device
LDAP / RADIUS Servers✅ YesServer address varies per site
Web Filter Profiles❌ NoComplex config structure — not a single value
Antivirus / IPS Profiles❌ NoFull profile — must use unique names
SSL/SSH Inspection❌ NoProfile group — not mappable
!
COMMON MISTAKE
If you import an object from the device layer that the policy layer doesn't support for per-device mapping, it causes a conflict. FortiManager must choose between its own value and the FortiGate value. Fix: create a uniquely named object and re-import.

Metadata Variables

A second mechanism for per-device variation. A $variable placeholder is used inside an address object or CLI template. Each device has its own value for that variable. Identified in the GUI by a magnifying glass + $ icon.

→
TIP
Per-device mapping solves variation at the policy/object level. Metadata variables + Jinja2 templates solve variation at the device configuration level. Know which layer each one belongs to.

Normalised Interfaces

Interface names vary across device models. FortiManager uses normalised interfaces to standardise names in the policy layer. A policy referencing LAN will substitute the correct physical interface (e.g. port2 or port4) per device during install.

  • Per-platform mapping — applies to all devices of the same model
  • Per-device mapping — customised per individual FortiGate
  • Normalised interfaces are case-sensitive — LAN ≠ lan
TOPIC B · INSTALL WORKFLOW

Install Operations & Revision Rollback

FortiManager gives you eight distinct operations for managing config flow between the policy layer, device layer, and FortiGate. Knowing when to use each is a common exam focus.

All Install Operations — at a Glance

OperationWizardPreviewWhat It Does
Install Policy Package✅ Full✅ YesSelect package + devices. Pushes policy layer → device DB → FortiGate
Reinstall Policy❌ Skipped✅ YesPackage + devices already known. Faster re-push of existing assignment
Install Device Settings✅ Preview✅ YesDevice layer only → FortiGate. No policy changes
Quick Install❌ None❌ NoImmediate device layer push. ZTP / confident changes only
Retrieve❌❌Captures FortiGate config → device DB revision. Does NOT update policy layer
Auto-Retrieve❌❌Automatic on device add. Same as Retrieve — no policy layer update
Revert❌❌Selects an older revision. Nothing pushed yet — must install after
Import❌❌Moves policies from a revision into a policy package

Rollback Sequence

1
Revert — Select the older revision from history. Nothing changes on FortiGate yet.
2
Install — Push the reverted config. Preview shown before anything commits.
3
Review Preview — Confirm the diff looks correct.
4
Confirm — Config lands on FortiGate.
!
EXAM TRAP
Revert alone does NOT restore the FortiGate config. It only selects the revision. You must still install. Many candidates miss this distinction.
SCENARIO — EXAM QUESTION STYLE
An admin has already pushed a policy package to 30 FortiGate devices. They make a small change to a firewall address object and want to re-push as quickly as possible with a safety review step. What is the correct operation?
Answer: Reinstall Policy. The package and devices are already assigned, so the wizard is skipped. FortiManager goes straight to the install preview, allowing the admin to confirm the diff before pushing.
TOPIC C · SCRIPTS

CLI Scripts, Tcl Scripts & Jinja2 Templates

FortiManager supports three scripting approaches. Choosing the right one depends on what you need to do and where it needs to run.

TypeLogicVariablesWhere It RunsBest For
CLI Script ❌ None ❌ None Device, Policy layer, or direct on FGT Flat command lists — create objects, set config
Tcl Script ✅ Full ✅ Yes Device, Policy layer, or direct on FGT Conditional logic — if/then/else, loops, error handling
Jinja2 Template ⚠️ Variables only ✅ Yes Device layer — inside Provisioning Templates Per-device CLI config with $variable substitution

Three Script Execution Contexts

  • Direct on FortiGate — auto-retrieve syncs device DB (unless policy changes are involved)
  • Device database — marks config as Modified; must install device settings to push
  • Policy package — flags package as Modified; must install policy package to push
!
EXAM TRAP
A script run on the device database does NOT automatically update the policy layer. And a script run on the policy package does NOT automatically update FortiGate — you must install after in both cases.
★
KEY DISTINCTION
Jinja2 is not a standalone script — it lives inside a Provisioning Template in the device layer. It renders $variables into CLI commands at install time. CLI and Tcl are standalone scripts you run manually or schedule.
USE CASE DECISION: Need to set 10 static config items → CLI Script Need to check a condition before acting → Tcl Script Need same config on 50 devices with different values → Jinja2 + Provisioning Template If it has if/then logic → always Tcl, never CLI
EXAM TIPS

What the Exam Tests

Session 03 maps directly to FortiManager central management scenarios. Expect questions on install operation selection, per-device mapping limits, and scripting context behaviour.

  • Revert ≠ Restore — Revert selects the revision. Install pushes it. Two steps, not one.
  • Install vs Reinstall — Not about first-time vs repeat. About wizard vs no wizard. Both have preview.
  • Per-device mapping limits — Security profiles (web filter, AV, IPS) do NOT support mapping. Addresses, VIPs, and IP pools do.
  • Script context matters — Policy package script → must install to reach FortiGate. Device script → must install device settings.
  • Jinja2 lives in provisioning templates — Not in the Scripts menu. Device layer only.
  • Normalised interfaces are case sensitive — LAN ≠ lan. Name mismatches cause install conflicts.
  • Retrieve ≠ Import — Retrieve captures to revision history. Import moves a revision into the policy package.
SCENARIO — SCRIPTING TRAP
A junior admin writes a CLI script that checks whether a static route already exists before adding it. Will this work?
Answer: No. CLI scripts cannot perform conditional logic. They are flat command lists with no if/then capability. This requires a Tcl script, which supports full programming constructs including conditionals and loops.
