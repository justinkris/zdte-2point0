Forward Traffic with the Zscaler Client Connector
⏱ 20 minutes · Forwarding Profile · Z-Tunnel 2.0 · App Profile
›
SCENARIO
Configure ZCC to securely forward all user traffic — regardless of protocol — to Zscaler for inspection. Enables firewall functionality, secure internet access, and multi-platform compatibility on/off trusted networks.
OBJECTIVES
  • Configure forwarding options to send all user traffic securely to Zscaler
  • Set up forwarding profiles and platform settings for Windows devices
  • Confirm Private Access, Internet Security, and Digital Experience are enabled
  • Confirm Corp: Client PC traffic is forwarded to Zscaler
3.1
Configure Traffic Forwarding Options
›
  1. Login to Experience Center: https://console.zscaler.com as student@<Student FQDN>
  2. Create a Forwarding Profile:
    • Infrastructure > Connectors > Client > Forwarding Profile for Platforms
    • Click Add Forwarding Profile
    • Name: HandsOnLab
    • Windows Driver Selection: Packet Filter Based
  3. FORWARDING PROFILE ACTION FOR ZIA:
    • On-Trusted Network: Tunnel
    • Tunnel version: Z-Tunnel 2.0
    • VPN Trusted & Off-Trusted Network: ✓ Same as "On-Trusted Network"
  4. FORWARDING PROFILE ACTION FOR ZPA:
    • On-Trusted Network: Tunnel
    • VPN Trusted & Off-Trusted Network: Same as "On-Trusted Network"
    • Click Save
  5. Add Windows App Profile:
    • Platform Settings > Windows
    • Click Add Windows Policy under App Profile
    • Name: HandsOnLab  ·  Rule Order: 1  ·  Status: Enable
    • Forwarding Profile: HandsOnLab
    • Install Zscaler SSL Certificate: On
    • User Groups: All
    • Click Add
→
WHY Z-TUNNEL 2.0?
Z-Tunnel 2.0 is necessary to intercept all traffic (any port/protocol) and tunnel it to ZIA for Firewall functionality. Z-Tunnel 1.0 only handles web (TCP/80, 443).
★
NOTE
ZCC v4.8+ on Windows defaults to Packet Filter driver, ignoring the Route-Based option.

Understanding forwarding profiles, Z-Tunnel versions, and app profiles is critical for deploying ZCC consistently across an enterprise fleet.

04
Configure Firewall Filtering Policy
⏱ 25 minutes · Default Block · ICMP/SSH Allow · Block WhatsApp
›
SCENARIO
Block WhatsApp at the network layer to prevent users from accessing it, while ensuring SSH and ICMP work for everything else.
OBJECTIVES
  • Verify the default firewall filtering policy blocks all non-web traffic
  • Test default rules that block ICMP and SSH
  • Create rules to allow outbound ICMP and SSH
  • Create a rule to block external apps like WhatsApp
  • Verify with practical, real-world testing
4.1
Test Non-Web Traffic with the Default Firewall Block
›
  1. Verify Default Firewall Policy:
    • Policies > Access Control > Firewall > Firewall Filtering Policy
    • Confirm the Default Rule is set to Block/Drop
    • Confirm there are no other rules allowing non-web traffic
  2. Test default policies on Corp: Client PC:
    • Open command prompt: ping www.google.com — should fail (request timeout)
    • Open puTTY; Host Name: github.com → Open — should fail (PuTTY Fatal Error after ~20s)
  3. End the unsuccessful sessions (close cmd, exit puTTY).
★
WHY THESE FAIL
With Z-Tunnel 2.0, ALL ports/protocols go to Zscaler. ICMP and SSH don't match Office 365 / Zscaler Proxy / Recommended rules, so they fall to the Default Block/Drop.
4.2
Configure Firewall Policy to Allow Outbound SSH and ICMP
›
  1. Create a Firewall Filtering Rule:
    • Policies > Access Control > Firewall > Firewall Filtering Policy
    • Click Add Firewall Filtering Rule
    • Rule Order: 1  ·  Status: Enabled
    • Rule Name: allow-outbound-icmp_ssh-student-any (format: [action]-[direction]-[services]-[source-scope]-[destination-scope])
  2. On Who, Where, Criteria tab → select your Student user account.
  3. On Services tab → Network Services → search and select ICMP, SSH → Done.
  4. ACTION: Network Traffic = Allow.
  5. Click Save and Activate from the cloud-arrow icon (top-right).
  6. Test ICMP: ping www.google.com — should now succeed.
  7. Test SSH: open puTTY → github.com → Open — should prompt for fingerprint / login.
4.3
Configure a Firewall Filtering Policy to Restrict Applications (WhatsApp)
›
  1. Create a Firewall Filtering Rule:
    • Policies > Access Control > Firewall > Firewall Filtering Policy
    • Click Add Firewall Filtering Rule
    • Rule Name: block_drop_all_whatspp_student_any
    • Rule Order: 2  ·  Status: Enabled
  2. Who, Where & When → User: Student Admin
  3. Action → Network Traffic: Block/Drop
  4. Applications → Network Applications: search for and select WhatsApp → Done
  5. Click Save & Activate.
  6. Test: navigate to https://web.whatsapp.com — should be blocked.
→
FW vs URL FILTERING
URL Filtering can block web.whatsapp.com but NOT a user with the WhatsApp desktop app. Firewall Filtering blocks at the network layer — full enforcement.
WHY THIS MATTERS

The ZIA Cloud Firewall enforces policy at layers 3–7 across ALL ports and protocols, not just HTTP/HTTPS — this is the critical difference between URL filtering (web-only) and firewall policy (everything). Understanding how to build rules that allow ICMP/SSH for operations while blocking consumer apps at the network layer is a foundational enterprise security configuration.

Configure SSL Inspection Policies
⏱ 30 minutes · SSL Inspect All · Cert Pinning · Bypass
›
SCENARIO
Enable SSL/TLS inspection to monitor and enforce policies on encrypted traffic. Most modern threats hide inside HTTPS — inspection provides visibility. Define SSL inspection for all destinations and exempt trusted/privacy-sensitive categories.
OBJECTIVES
  • Enable SSL inspection for all encrypted traffic
  • Verify Zscaler's certificate installation on the Windows Corp: Client PC
  • Analyze and resolve certificate pinning errors
  • Analyze SSL inspection logs and identify inspection or bypass events
★
ROOT CA INSTALL
The Zscaler Root CA is installed when ZCC is installed. On Windows it lives in: (a) the System Cert Store (Trusted Root Certification Authorities), and (b) the Firefox Cert Store (based on App Profile).
5.1
Enable SSL Inspection for All Destinations
›
  1. Verify current SSL Inspection status:
    • Open Chrome Incognito on Corp: Client PC → www.wikipedia.org
    • Click site info icon → Connection is secure > Certificate is valid
    • Note: cert is from the destination web server (no Zscaler interception yet)
  2. Enable SSL Inspection:
    • Policies > Common Configuration > SSL/TLS Inspection > SSL/TLS Inspection Policy
    • Click + Add SSL Inspection Rule
    • Rule Order: 1  ·  Rule Name: SSL Inspect All
    • ACTION → Inspect
    • Click Save & Activate
  3. Verify inspection status:
    • Close/refresh incognito browser to apply policy
    • Reopen incognito → www.wikipedia.org
    • Site info → cert is now signed by Zscaler
5.2
Verify Zscaler CA Installation [Optional]
›
  1. Open certmgr from Windows search.
  2. Navigate to Trusted Root Certification Authorities > Certificates.
  3. Confirm:
    • Zscaler Root CA Certificate is listed
    • Certificate is not expired
  4. Verify via Chrome:
    • Open chrome://certificate-manager/
    • Click Local certificates → View imported certificates from windows
5.3
Review Certificate Pinning Errors
›
Cert pinning hardcodes a trusted cert into an app to defeat MITM. With SSL inspection, the pinned cert won't match Zscaler's — connection fails. Two common fixes follow.
  1. Recreate the pinning error:
    • Download Threema Private Desktop for Windows from https://threema.com/en/download (an .msix file)
    • Open PowerShell from Start menu and run: Add-AppxPackage -Path .\Downloads\threema-desktop-latest-windows-x64.msix
    • Open Threema Beta from Start → observe the error
  2. Configure an SSL Bypass Rule:
    • From SSL Inspection page → Add SSL Inspection Rule
    • Rule Order: 1  ·  Rule Name: Bypass Threema
    • Cloud Applications → Instant Messaging → select Threema → Done
    • Action: Do Not Inspect
    • Save and Activate
  3. Reattempt Threema:
    • Task Manager → end any running Threema task
    • Open Threema Beta from Start — should now work
  4. Analyze SSL Inspection & Bypass logs:
    • Logs > Web Insights > Logs
    • Timeframe: Last 1 hour (or longer)
    • Add filters: SSL Inspected and Bypassed Transaction
    • Click Run Query
★
NOTE
Allow ~5 minutes for logs to populate.
WHY THIS MATTERS

SSL Inspection is the prerequisite that unlocks virtually every advanced ZIA security control — without it, all HTTPS traffic is an opaque tunnel Zscaler cannot inspect. Properly configuring bypass rules for certificate-pinned and sensitive-category traffic prevents SSL inspection from breaking legitimate applications while still providing full visibility into the web traffic that matters most for security.

★
NOTE
Allow ~15 minutes for logs to become available.

DNS Security intercepts malicious domains at the resolution layer — before any TCP connection is attempted — making it one of the most effective and lowest-latency controls for blocking C2 callbacks, malware distribution, and phishing infrastructure. DNS Insights logs provide forensic evidence of blocked query attempts that would otherwise be invisible to HTTP-level monitoring.
